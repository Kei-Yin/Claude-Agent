# MyClaude 项目介绍与面试问答

本文以 2026-10-21 的代码和本机验证为依据。介绍时先讲 Python Agent 主线，再按岗位需要补充长期记忆、A2A 或 WDBuddy。个人贡献请按实际负责内容调整：参考的项目思路、已有代码、AI 辅助生成和自己完成的设计、调试、验证应说明清楚。

## 30 秒开场

> MyClaude 是一个本地编程 Agent 项目，参考了 Claude Code 的交互方式。用户用自然语言描述任务，系统通过大模型决定下一步操作，再在本机读取、创建、修改文件或执行命令，把执行结果反馈给模型，循环到任务结束。我主要想研究的是工具调用的可靠性、历史经验复用，以及如何验证任务真的完成。目前 Python 主流程已经通过真实模型的文件读写测试，仓库中还有一个独立的 Electron 桌面工作台 WDBuddy。

如果尚未实际参与某个模块的设计，把“我设计了”改为“项目中采用了，我重点分析和验证了”，再讲清你确实完成的部分。

## 2～3 分钟完整介绍

> 这个项目的出发点是：大模型可以生成代码，但要完成本地开发任务，还需要知道读哪个文件、调用什么工具、如何根据执行结果继续，以及什么时候算真正完成。所以我以一个终端编程助手为主线，把自然语言输入到本地产物交付的过程串起来。
>
> Python 侧的核心是 QueryLoop。它先组装用户输入、历史消息和相关记忆，再请求模型。模型输出 XML 格式的工具操作，解析器把这些文本转换为具体的工具调用，执行后将结果写回消息，让模型继续决策。比如先读文件，再修改，再运行检查，最后用独立的 done 响应结束。CLI、模型调用、工具执行和记忆管理分别放在不同模块，便于定位问题和扩展。
>
> 我会重点讲可靠性这一块。Agent 不能仅凭一段“操作成功”的文字判断完成：文件工具必须保留真实的失败或阻断结果，API 错误应该终止任务，重复调用同一工具需要熔断，测试模式要给出结构化结果和正确退出码。项目里确实遇到过创建被阻断却返回成功提示，以及重复读文件后仍以成功退出的问题，后续修复和回归检查就是围绕这些情况展开的。
>
> 另一个方向是长期记忆。系统从 Markdown 会话日志中提取经验，用 Markdown 和元数据保存，再根据策略做 FAISS 粗召回和模型精排，在预算内注入后续任务。这里实现的是经验复用机制，还没有用对照实验确认它提升了多少任务成功率，也不能把它说成模型完成了训练或自动改进了自身代码。
>
> 仓库中的 WDBuddy 则探索桌面产品形态，使用 Electron、React 和独立的 TypeScript Runtime，通过 IPC 和 JSON-RPC 通信，加入任务存储、规划执行和产物展示。两套应用目前是独立实现。现在已经验证了 Python 的真实模型读写流程、桌面构建和启动；桌面沙箱还有测试失败，持久化恢复也未接通。下一步会先补齐权限边界和可重复的任务验收，再评估记忆效果及产品化能力。

这段介绍的顺序是：要解决的问题 → 一次请求如何执行 → 最有价值的工程难点 → 可扩展方向 → 已有证据与下一步。不要逐个背目录或堆叠技术名词。

## 如何讲清架构

### Python 主链路

```text
用户请求
  → CLI 接收和展示
  → QueryLoop 管理轮次、消息、记忆、终止条件
  → chat_llm 调用模型
  → tool_executor 解析工具并执行
  → 真实结果进入消息和日志
  → 下一轮模型决策 / done / 失败终止
```

| 层次 | 关键文件或目录 | 可以讲清的职责 |
| --- | --- | --- |
| 入口与交互 | `src/myclaude.py`、`src/cli/mycli.py` | 参数、交互命令、显示、非交互测试模式 |
| 执行控制 | `src/query/query_loop.py` | 多轮循环、工具反馈、重复调用防护、失败状态 |
| 模型适配 | `src/query/chat_llm.py` | OpenAI 兼容客户端、错误处理、响应和 usage |
| 工具协议 | `src/llm_tool/tool_executor.py` | XML 解析、工具分发、文件操作真实回执 |
| 长期记忆 | `src/memory_ex/` | 日志提取、存储、召回、精排、预算内注入 |
| 配置 | `src/utility/config_loader.py`、`config/` | 配置合并、provider 选择、相对路径解析 |
| 测试实验 | `src/A2A/` | 测试服务编排、执行和报告 |

面试官让你“走一遍代码”时，选一个请求跟踪到工具结果返回即可，再补充异常分支。不要只展示启动界面。

### WDBuddy 桌面架构

> 渲染进程负责 React 界面和状态；Electron 主进程负责窗口、存储及凭据；Agent Runtime 是独立 Node 子进程，负责规划、工具执行、重规划和验证。前两层通过 IPC 通信，主进程和 Runtime 通过标准输入输出上的 JSON-RPC 通信。

可解释的取舍：进程边界减少任务执行与界面的耦合，Runtime 可单独测试，但也引入协议同步、错误传播和恢复状态管理的成本。进程拆分本身不提供完整的命令权限隔离，也不自动实现崩溃恢复。

## 三个值得展开的工程问题

### 1. 如何避免工具“假成功”

**具体问题**：已有文件禁止被创建工具覆盖，但摘要包装逻辑曾将底层阻断结果包装成“文件已创建”；精确替换失败也有类似问题。上层模型会基于错误观察继续推理。

**修复思路**：保留底层失败和 `[BLOCKED]` 信息，只在真实操作成功后生成成功回执。回归检查不仅断言返回文字，也检查文件内容，确保原文件没有被覆盖、成功替换确实落盘。

**可以口述**：

> Agent 的下一步决策依赖工具观察结果。如果工具把失败说成成功，模型再强也会沿着错误状态继续。我优先修复真实状态向上传递的问题，并通过文件内容和工具回执同时验证，避免只测试一条成功提示。

**进一步改进**：统一类型化的工具结果，例如状态、错误码、产物路径和可重试标记，让 UI、模型反馈和测试报告共享同一个事实来源。目前 Python 侧仍主要使用消息字典和文本回执，这属于后续改进。

### 2. 如何处理多轮调用和异常终止

**具体问题**：真实测试曾出现工具反馈用中途 `system` 消息插入，随后模型重复读文件；重复调用熔断后，测试结果又未体现任务失败。消息格式只是其中一个已发现问题，不能仅凭一次成功就断言所有重复行为都由它引起。

**修复思路**：保留开头的系统提示词，将运行中工具结果作为带前缀的 `user` 消息反馈；API 错误立即终止；连续相同工具、轮数耗尽等终止条件设置失败状态，由测试模式转成非零退出码。

**验证证据**：后续真实 DeepSeek 测试完成 `file_view → create → 独立 done`，标记文件内容正确；失败分支由不调用模型的回归测试覆盖。

**可以口述**：

> 我把正常完成、执行失败和保护性中止区分开。熔断只是让循环停止，不能代表任务完成，所以必须将失败状态传到调用方，再检查退出码和实际产物。

**进一步改进**：把状态机与副作用执行分开；为合法重试、分页读取和长任务设计更细的规则，避免硬性读取次数限制误伤正常任务。对工具超时、取消和幂等性增加任务级测试。

### 3. 如何让“能运行”变成可复现的验证

**具体问题**：有 conda 不代表前端有 pnpm；有 `openai` 包不代表密钥有效；系统 Node 的原生模块不一定兼容 Electron；构建成功也不代表桌面静态资源和数据库 schema 已正确进入输出目录。

**处理方式**：明确两套环境，固定仓库使用的 pnpm 版本，补充 Electron 原生模块准备脚本、资源复制和 Windows 启动入口；Python 使用指定环境启动、依赖清单和本地密钥模板。

**验证方式**：检查真实模型文件产物；实际启动 Electron，检查窗口、preload API 和数据库接口；在普通 Windows PATH 中验证启动，避免只在开发工具自带的环境中成功。

**可以口述**：

> 我把运行验证拆成了依赖可用、进程启动、模型连通、工具产生副作用和任务验收几个层次。这样能区分环境问题与 Agent 逻辑问题，也能发现“构建通过但应用打不开”的情况。

## 高频追问与回答要点

### 这和直接调用聊天 API 有什么区别？

聊天 API 提供模型推理；这里还实现了任务循环、工具协议、本地副作用、结果反馈、终止条件、日志和验收入口。价值在于把一次文本生成组织成可观察、可验证的任务执行过程。是否执行正确仍需产物检查。

### 这是 ReAct、多 Agent，还是工作流？

Python 主循环可以理解为 ReAct 式的“决策—行动—观察”过程，但没有必要声称完整复现某个框架。主编程循环主要由一个模型驱动工具执行；`src/A2A/` 是另一个测试编排实验，WDBuddy 的 Planner/Executor/Verifier 也不自动等于多个独立智能体。

### 为什么用 XML，而不用原生 function calling？

当前实现使用文本协议，方便观察和调试工具请求，也可以在不同文本生成接口上复用。但代价是需要处理转义、嵌套、代码示例误触发及不完整标签。后续可以把工具 schema 和结构化结果抽象出来，在支持的 provider 上接入原生工具调用，同时保留文本协议适配。不要声称 XML 天然更安全或更可靠。

### 为什么 Python 核心使用同步循环？

单任务编程过程中，后一步通常依赖前一步的执行结果，同步调用链便于分析和调试。当前没有证明需要高并发。若未来支持多任务并行，再引入调度、超时、取消和副作用隔离；A2A 服务和桌面 Runtime 的异步实现属于其他边界。

### “流式”具体体现在哪里？

模型响应以 stream 方式读取，代码会收集内容、推理内容和 usage。Python CLI 主要在收集后展示，不能将打字机效果等同于逐 Token 的网络到终端实时渲染。桌面端有独立的事件传递实现，需要分别验证。

### 记忆系统是不是 RAG？

有检索增强的思想，但检索对象主要是项目经验和会话提炼的记忆。当前链路是 Markdown 日志提取 → 条目与元数据存储 → 向量候选召回 → 模型精排 → 按预算注入。它不是微调，也不保证所有对话都会自动变成有效记忆。辅助模型、索引和数据为空时的行为都需要检查。

### 怎么证明记忆有效？

目前没有足够数据证明收益。下一步应固定任务集、模型配置和预算，对比有记忆/无记忆的任务成功率、错误重复率、延迟与 Token 成本，并人工检查召回相关性。成功率由真实产物或测试决定，LLM 判定只作为补充。

### “自我进化”已经做到什么程度？

实现了记忆提取、压缩整理和经验归纳机制，当前自动整理、自动进化配置关闭。还没有证明系统可以自主改进源代码并通过回归验证，也没有完成持续学习效果评估。把它表述为探索方向更准确。

### 安全性如何保证？

先区分实际强制与提示词要求。Python 工具有禁止直接覆盖、精确替换、重复调用等检查，但命令仍在本机权限下执行，没有完整沙箱。WDBuddy 实现了路径守卫和权限决策层，然而 Windows 下还有 5 项测试失败，Ask 模式也需要继续核验只读约束。权限检查应放在副作用发生前，后续还需要隔离、确认和回归测试。Python 模型客户端的 `verify=False` 也是需要修复的具体问题。

### 如何判断任务结束？

独立 `<done>` 是模型协议中的正常完成信号，API 错误、重复调用和轮数限制等是异常结束。测试模式记录退出码、错误、工具调用和会话内容，但这些还不能自动证明任意需求都被满足，必须结合确定性验收条件，比如文件内容、测试结果和修改范围。

### 如何处理成本与上下文增长？

已有轮数限制、重复读取防护、Token 统计和记忆注入预算；这些还不是完整的任务成本管理。默认最大轮数和输出上限偏大，应按 provider 能力和具体任务设置。上下文压缩代码存在，但尚未验证主循环接入，不能称为已经解决无限上下文问题。

### WDBuddy 能恢复中断任务吗？

界面和数据库具备部分中断状态与检查点接口，但运行时仍使用内存检查点，跨进程持久化恢复尚未接通，暂停/恢复也没有完整实现。后续要让状态持久化、恢复协议和工具幂等性形成闭环，再进行崩溃恢复测试。

### 用了 AI 辅助开发，你的贡献是什么？

按真实经历说明需求拆分、阅读和理解、方案选择、具体修改、故障定位、测试和验收。挑一个你能展示前后行为、解释根因并回答取舍的提交展开。AI 生成了部分代码时直接说明；不能把未读懂或未验证的模块包装成自己的独立设计成果。

## 3～5 分钟现场演示

1. **开场 30 秒**：说明输入、工具执行和预期产物，指出 Python CLI 与桌面应用的边界。
2. **检查环境**：确认 `LLMs` 的解释器、已选择的主模型、网络和配额。不要在投屏时展示密钥文件。
3. **真实调用**：运行根目录 README 的带时间戳演示。任务限定为读取配置首行、创建标记文件、独立 done，过程短且有明确验收标准。
4. **展示证据**：打开产物，检查 JSON 的退出码、错误和工具顺序，解释为什么不能只看一句“成功”。
5. **展示回归**：运行 `python -X utf8 -m unittest src.utility.test_runtime_regressions -v`，选一个“已有文件不能被覆盖”的测试解释。
6. **可选桌面展示**：预先启动 `wdbuddy/start.bat`，展示工作台和实际已验证的能力。不要临场承诺账号体系、跨进程恢复或尚未验证的办公流程。

真实 API 演示失败时，保留错误，按 provider、认证、网络和工具结果分层定位；可以转而展示预先保留的真实记录，并明确说明记录与现场执行的区别。面试前至少完整预演一次，确认任务不会修改正式源文件。

## 下一步修改优先级

| 优先级 | 工作 | 完成标准 |

| P0：交给他人使用前 | 修复桌面沙箱失败、核对只读模式、恢复 TLS 校验、收紧 Python 副作用权限 | 正常和越权场景有明确结果，Windows 权限回归通过 |
